## Design Specificity Verdict

The tables feel authored for a shoe-store operating system rather than copied from a generic admin template. Amber monospaced product codes, dual-currency values, stock severity, movement types, return outcomes and audit expansions reinforce the product's “El Taller de Caja” direction.

The requested uppercase header rule is already centralized in `src/components/ui/table.tsx`: every `TableHead` uses 10px semibold uppercase styling. Plain string headers and sortable JSX headers therefore render consistently even when source labels use sentence case. The right fix is to preserve this central CSS rule, not uppercase every string literal by hand.

Returns does not actually use shorter rows: the master register still inherits the canonical 30px row and 13px cell geometry from `DataTable`. It selectively uses 12px for audit metadata. That distinction is effective and should remain local; it should not become the global body size. The expanded return ledger and constrained modal tables are legitimate candidates for a named compact variant.

The deterministic detector reported 88 advisory findings: 84 font-size, 3 color and 1 radius. Most table-adjacent 10px findings—including `TableHead`—are false positives against documented table guidance, although they reveal that the 10px table-label token is not represented in the formal typography ramp. The 9px currency-unit labels in expanded returns are genuine off-ramp values. The 3px scrollbar radius is non-actionable for table anatomy.

Browser overlays were unavailable because the configured Playwright Chrome binary was missing at `/opt/google/chrome/chrome`; no visual overlay was created. Source evidence and the detector were used as the fallback signal.

## Overall Impression

The system already has a strong operational table foundation: compact, warm, keyboard-aware and tailored to real store data. Its biggest opportunity is to turn the currently implicit table grammar into two explicit density modes—operational and compact—and make numeric presentation as consistent as the surrounding anatomy.

## What's Working

- `DataTable` centralizes sticky uppercase headers, 30px/13px rows, striping, hover/focus behavior, loading, empty states, pagination, labelled scroll regions and keyboard activation.
- Module-specific semantics are strong: Inventory communicates stock risk, Movements preserves audit deltas, Cash closes reads like a daily ledger, and Returns exposes a credible movement-and-credit model.
- Product codes, truncation tooltips, semantic badges, date formatting and retryable errors create a coherent, professional scanning experience across registers.

## Priority Issues

### [P1] Density is consistent inside `DataTable`, but fragmented across the full table system

**Why it matters:** The app currently has an unnamed 30px/13px operational mode, several 12px compact tables with different horizontal padding, and raw confirmation tables. Similar tables can drift because spacing and cell anatomy are repeated locally.

**Fix:** Add explicit `operational` and `compact` density variants to the shared `Table`/`DataTable` layer. Let the variant own header height, body font, row height, horizontal padding, skeleton geometry and empty-state scale. Keep module columns and business semantics local.

**Suggested command:** `$impeccable layout`

### [P1] Returns compresses the financial conclusion into one hard-to-scan cell

**Why it matters:** `Resultado` combines an outcome label plus USD and Bs. figures without local currency labels or cross-row alignment. Operators must remember the amount order, and values cannot be compared vertically.

**Fix:** Preserve the compact row, but split semantic outcome from right-aligned USD/Bs. columns, or use a two-line cell with explicit currency labels and aligned amounts. Keep the expanded ledger for reconciliation detail.

**Suggested command:** `$impeccable layout`

### [P1] Numeric data lacks one consistent typographic and alignment treatment

**Why it matters:** Most quantities, rates, timestamps and amounts use `tabular-nums` but not the prescribed mono data face. Transaction exchange rate is left-aligned, while equivalent numeric fields are right-aligned elsewhere. The visual system is more consistent than the data grammar.

**Fix:** Create a reusable data-cell treatment for dates, quantities, rates and money: 13px mono, tabular figures, stable weight, right alignment for comparable numeric columns. Keep prose, names and descriptions in Inter. Do not force the 12px Returns metadata treatment globally.

**Suggested command:** `$impeccable typeset`

### [P1] Inventory exposes a blank actions column to employees

**Why it matters:** The header remains visible while non-admin row cells return `null`, creating empty scan space and implying unavailable capabilities.

**Fix:** Build the actions column only for administrators. Keep row-to-detail navigation as the employee path.

**Suggested command:** `$impeccable distill`

### [P2] Shared states and repeated confirmation anatomy can still drift

**Why it matters:** Skeleton rows do not match the loaded 30px rows. Page-level error branching is repeated because `DataTable` has no integrated error API. Batch, sale and return confirmation dialogs duplicate the same desktop-table review pattern; pending-operation tables repeat compact mechanics and empty states.

**Fix:** Make skeletons density-aware; centralize DataTable error/retry and compact empty-state configuration; extract a confirmation-line table/review-list primitive. Share presentation mechanics, not return, sale or inventory business logic.

**Suggested command:** `$impeccable polish`

## Persona Red Flags

**Alex, power operator:** Returns cannot be rapidly compared or sorted by financial result because outcome and both currencies are folded into one cell. Employees also scan past a permanently blank Inventory actions column. Static neutral sort chevrons across wide registers add a small but repeated noise tax.

**Sam, keyboard/screen-reader operator:** Labelled scroll regions, focusable expandable rows and `aria-expanded` are strong. The previous-description pencil in Movements is hover-only/non-focusable, so audit evidence is inaccessible from the keyboard. The two Returns amounts also lack enough local semantic differentiation.

**Empleado de tienda bajo presión:** The compact density supports fast scanning, but a complicated exchange forces reconciliation between a dense result cell, a five-column movement ledger and a four-part summary. The answer needs clearer financial structure, not larger rows.

## Cognitive Load

Moderate: 3 of 8 checks fail. Single focus, grouping, one-decision-at-a-time, minimal choices and progressive disclosure pass. Visual hierarchy, working-memory demand and chunking fail mainly in Returns: outcome plus two currencies compete in one cell, and the expanded ledger and financial summary demand simultaneous reconciliation.

## Emotional Journey

The default registers feel controlled and trustworthy. The low point is a complex return, when the user needs reassurance that credit, replacement purchase, difference and exchange rate reconcile. The expanded summary restores confidence, but the master row should make the conclusion legible before expansion.

## Minor Observations

- Users legitimately needs a taller two-line identity row; name it as an `identity` row/cell pattern instead of treating it as accidental drift.
- Modal working tables are appropriately denser than page registers, but should consume the same named compact density.
- Use the semantic return token instead of raw `text-orange-500` for return counts in Cash closes.
- Keep only the active sort icon continuously prominent; reveal or further soften the neutral icon on hover/focus.
- Document the valid 10px table-label token in the typography authority so the detector stops flagging a deliberate rule.

## Questions to Consider

- Should Returns' `Resultado` answer only what happened, or also present two independently comparable amounts? If it must do all three, why is it one column?
- Is the Inventory actions column universal record anatomy or an administrator-only capability?
- Should compact tables mean one exact density everywhere, or are there truly multiple constrained contexts that need separate named variants?
